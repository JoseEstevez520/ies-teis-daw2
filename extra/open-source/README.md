# Open source

Código que su autor publica para que cualquiera lo vea, lo use y lo mejore. Muchas veces
lo que vas a construir ya existe, hecho y probado.

## Busca antes de construir

Es muy típico ponerse a hacer desde cero algo que ya está hecho, y mejor. Antes de
empezar, busca. Lo que hagas depende de lo que encuentres:

| Si encuentras | Haz |
|---|---|
| algo maduro que hace lo que necesitas | **úsalo**, como dependencia o tal cual |
| algo parecido, pero no justo lo tuyo | **adáptalo** con un fork, o sácale ideas |
| nada | **constrúyelo**, y publícalo para el siguiente |

**Si ya hay algo maduro que hace lo que necesitas, úsalo**: tu tiempo va a lo que es solo
tuyo.

## Cómo buscar

Pídeselo a un agente: le cuentas qué quieres hacer y busca por ti. Que no se quede con el
primero: que mire si se mantiene y qué licencia tiene. **Un buen proyecto se mantiene,
tiene licencia y encaja con lo que usas**; las estrellas solas no lo dicen.

## Qué puedes aprovechar

Según lo que necesites, de un proyecto sacas cosas distintas. Ejemplos reales, con su
licencia:

- **Usarlo tal cual:** [Torph](https://github.com/lochie/torph) (MIT) anima un texto
  cuando cambia. La librería de componentes de la web del repo lo usa en vez de hacerlo de
  cero.
- **Ver cómo se hace:** [spring-petclinic](https://github.com/spring-projects/spring-petclinic)
  (Apache-2.0), el proyecto de ejemplo oficial de Spring, con controladores, repositorios,
  validación y tests bien organizados.
- **Coger piezas:** [shadcn-vue](https://github.com/unovue/shadcn-vue) (MIT), componentes
  de Vue pensados para copiarlos a tu proyecto y cambiarlos.
- **Sacar ideas:** [OpenUI](https://github.com/wandb/openui) (Apache-2.0) genera
  interfaces a partir de una descripción en texto.

> [!WARNING]
> La licencia dice qué puedes hacer con el código. MIT o Apache-2.0 te dejan usarlo casi
> para todo, citando de dónde viene. **Sin licencia no puedes usar su código**, aunque
> esté a la vista ([por qué](https://choosealicense.com/no-permission/)).

## Fork y pull request

Cuando lo que encuentras es parecido pero no justo lo tuyo, haz un fork: tu copia del
proyecto, en tu cuenta, para cambiarla sin tocar el original.

1. **Haz el fork:** en la página del proyecto en GitHub, el botón **Fork**.
2. **Trabaja en tu copia:** clónala, arráncala y cámbiala. Es tuya, puedes romperla sin
   miedo.
3. **Si mejoras algo, propónselo:** un **pull request** le enseña al autor tus cambios
   para que los revise y, si le valen, los añada al original.

**Con un pull request, lo que arreglas para ti lo aprovecha todo el que usa el proyecto.**

## Publica lo tuyo

Lo mismo al revés: si construyes algo que no existía, publícalo. Con un README que diga
qué es y cómo se arranca, y una licencia ([cómo elegirla](https://choosealicense.com/)),
otros pueden usarlo, avisarte de fallos y ayudarte a mejorarlo.

Este repo es la misma idea, a escala de clase: cada uno aporta apuntes y herramientas, y
todos aprovechan lo de los demás en vez de hacerlo cada uno por su cuenta.

**Publicar es la otra mitad de aprovechar: alguien, en algún sitio, está buscando lo que tú
ya has hecho.**
